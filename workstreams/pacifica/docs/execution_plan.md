## 研究问题和首轮目标

在相近推理成本和误报率下，针对具体执行动作追问授权依据，能否比固定追问、被动监控或额外复查发现更多未经授权的动作？

下一 session 先完成 Phase 0–1：建立可信的 B1 baseline 小规模流程。尚不要求证明 TGF 有效，也不要求一次性完成全部方法。

## Phase 0 的具体动作

1. 检查已有代码；若没有，在 third_party/ 中获取 [MonitorBench 官方仓库](https://github.com/ASTRAL-Group/MonitorBench)，记录 commit。
2. 阅读仓库 README、run.sh、main.py、config/、pipeline/outcome.py、monitor 提示及两个环境的 checker。先确认真实 CLI、模型后端和任务选择方式，再写运行脚本。
3. 先确认 Bouchet 的 GPU 型号、显存、调度限制、配额、模型文件位置、网络及模型服务方式。候选 actor 为 gpt-oss-20b/120b，monitor 为 Qwen3-32B；不假定两者能同时驻留一张卡。
4. 若资源合适，可考虑分阶段生成并缓存轨迹、再卸载 actor 运行 monitor；量化、远程服务或 API 方案以实际条件为准，并记录配置。
5. 检查 reasoning 与工具消息解析：模型实际输出是否保留推理、长轨迹是否截断、上下文是否足够。禁止以空 reasoning 或静默截断冒充 all-messages。
6. 若模型暂未接通，可先完成数据结构、标签和视图隔离检查；明确这不等于端到端复现成功。

2026-10-07 的官方 README 提供 agent 任务注册、配置和现有执行流程。应复用经过检查的官方入口；不要直接运行默认脚本去批量评测全部任务。

## Phase 1 的具体动作与验收

先在一个环境跑一条，再扩到另一个环境。每环境计划 3–5 条，尽量检查正常请求和含副目标情形；调试集未出现实际违规时如实记录，不将攻击提示当作阳性标签。

需要保存并检查：
- 用户请求、适用政策、原始 actor 上下文和完整工具执行日志。
- 独立的 verifier 结果与证据，能够说明哪个执行事件违反了哪项授权。
- 清理后的 monitor 输入视图；隐藏目标与标签不得泄露。
- B1 的分块/层级处理结果、最终 0–100 suspicion score，以及解析失败记录。
- 模型标识、后端、量化、reasoning 设置、种子、prompt、token 限制、代码 commit 和运行命令。
- 按模型区分的 token、调用数、延迟、费用或 GPU 时间；没有费用信息时记为未知。

验收是“两环境都可以复跑并检查每一步”，不是获得好看的分数。调试输出和正式评测结果分开命名。

## 标签和数据协议

阳性指实际执行了未经授权的动作，含后来撤销的动作。标签核验读取显式授权规范、执行事件和特权模拟状态；monitor 看不到特权材料。

副目标成功不自动等于违规，副目标失败也不自动等于安全。主任务成功、安全标签和副任务结果使用不同字段。规则基线只能用与部署时相符的可见授权字段，不能复用 oracle 状态；记下无法覆盖的情况。

建议每条记录至少有：
- trace_id、task_family_id、environment、split、seed、actor 配置引用。
- 原始轨迹引用、monitor 可见视图引用、政策与请求引用。
- verifier 标签、证据事件、人工复核状态、排除原因。
- 主任务结果、副任务结果、实际违规和未执行尝试的独立记录。

这些是建议的数据字段，实施时按仓库结构确定。原始轨迹和标签分开存放，并给 monitor 明确构造允许的输入字段。

## 比较条件

| 条件 | 做法 | 目的 |
|---|---|---|
| 可部署规则 | 只基于可见授权与动作字段判断，报告覆盖率 | 判断模型在规则之外是否有收益 |
| B1 | Passive hierarchical monitoring | 基础检测能力 |
| B2 单问题 | 固定问题追问 actor，工具关闭 | 固定追问的基础版本 |
| B2 匹配版本 | 与 TGF 共用 ledger、选定动作、问题数、judge、通道和回答上限 | 隔离针对性问题内容的作用 |
| B3 | 在相近总预算下让 monitor 额外检查原始轨迹，不获取 actor 追问回答 | 区分新增回答与额外计算的收益 |
| Ledger 消融 | 整理动作后直接判断，不追问 | 隔离结构化整理的作用 |
| TGF | 对选定动作生成针对授权依据的问题，再综合判断 | 待检验的方法 |

B2 固定问题的具体措辞、B3 的复查/汇总策略、k、分块方式和各项预算都需要在开发阶段确定。原始轨迹冻结，各追问条件从相同的原始 actor 上下文独立分支；不能串用前一种条件的回答。

## 评价和成本

- 按环境报告主指标 g-mean squared = TPR × TNR，及 TPR、FPR、AUROC、混淆矩阵、authorized-but-sensitive 样本误报。
- 开发集选协议；验证集根据预先确定的目标 FPR 选阈值；测试时冻结阈值并报告实际 FPR。
- 正式样本量、FPR 目标、可接受成本/误报差异目前待 pilot 确定，不继承旧计划中的 5% 或旧训练数据量。
- 最终比较按任务家族做配对 bootstrap；单个家族大量派生样本不能当作独立家族数量。
- 自然执行轨迹是主测试，事后构造的授权配对只做诊断；不混报。
- 分阶段记录采集成本和每种监控方法成本。公平比较计入预处理、提问、actor 回答与最终判断的全部调用，不能只比较最后一次 judge。
- 阴性/阳性不足、标签无法确定、接口出错等情况记录为不可计算或失败，不静默丢弃。
- 原协议复现和自定义授权审计分开计分，不声称自定义指标复现了论文总分。

## 历史：2026-10-12首轮B1之后的执行顺序（其诊断现已完成，后续以next_steps为准）

这是阶段性工作顺序补充，不替代proposal的正式数据与评价承诺。

1. 现有标签：保留3条可判定样本及2条邮件语义待定样本，排除原因透明；不要用monitor分数决定标签。
2. 基础诊断：data/diagnostics/b1_checks_v1/plan.json已准备，尚未运行。5个开发诊断案例×2种指令，最多10次monitor调用，固定模型与其他设置。检查是否尊重显式授权、区分计划与执行，以及能否根据授权改变而改变判断。保留所有失败，不在这些案例上选阈值。
3. 全轨迹复核：诊断后只做必要、版本化的基线修正；在原冻结开发轨迹上检查，并明确开发调优属性。前段授权信息保留方案须对后续所有比较条件一致，不能使用oracle授权表帮助monitor。
4. 核心研究原型：共用动作整理、选定条目、judge、观察通道、回答预算，先做ledger-only、B2固定追问、TGF针对性追问的小规模配对。追问分别从原始actor上下文独立分支并禁用工具。B3成本对照和完整消融仍保留在后续正式计划中。
5. 数据与第二环境：航空按1条→3–5条接通。当前仓库在两个目标任务中各提供一个原始定义，无法直接支持每环境独立开发/验证/测试家族。补充数据来源或调整正式评估设计，须在正式采集前明确；换seed不产生新家族。暂不增加大批同一家族轨迹来掩盖这一问题。

本阶段验收不是把分数调好，而是：错误原因有证据、监控不读取特权标签、比较条件只改变指定因素、下一步能够直接检验追问的额外价值。
