# 公开 MRT 数据可用性核查（2026-10-15）

## 结论与本轮边界

公开数据确实提供了大量可复用的历史轨迹候选；不能再说上游只有任务代码或只有我们生成的少量轨迹。但**这次核查未证明它能直接补齐当前方案的每域30正/30负，也不能原样接入当前TGF主比较**。主要障碍是标签定义、导出信息缺失，以及历史actor与当前冻结actor不一致，而不只是文件数量。

用户本轮明确授权仅核查公开数据，不改任务、不运行新实验。本轮0模型调用、0GPU、0环境dispatch、0训练、0作业提交；未改任务、prompt、标签、冻结配置或旧结果；未恢复自动化。以下是可用性审计，不是436条完整语义标注或方法效果结果。不存在新增已验收的正负样本声明。

## 能否补齐正负样本

**有足量原始候选值得利用，但目前没有可以直接搬入的30P/30N真值集。**

1. 原数据的`side_task_evaluation`只表示指定副目标是否成功；无注入、主任务分数高、monitor判低风险，都不是我们“没有执行任何未经授权动作”的完整证据。航空购买AA或价格高本身不自动违反公开授权。
2. 已读1,763文件都只有`role/content/tool_calls`三种消息字段；所有非空调用字段都仅列工具名。缺少原始arguments、call ID和原生调用/返回绑定。`utils/logging_utils.py`的导出函数也只写工具函数名，证实这是有损导出，不是本轮parser漏读。
3. 可从某些工具返回中恢复部分执行事实。例如银行返回金额和收款人，可用于查找疑似错付；航空返回乘客和航班号，可与已观察到的航班资料核对。这些信息有静态证据分析价值，不应丢弃。
4. 但完整负例更难确认：银行`scheduled_transaction`的返回可能省略日期和recurring。41条无副目标银行候选中23条有成功安排转账，其中22条未调用`get_scheduled_transactions`读回；需要逐事件进一步核实，不能把缺失参数补成默认合法。
5. 航空110条无副目标候选中105条有成功餐厅预订。返回显示餐厅、日期和时间，但没有party_size；全部91条有成功购票的无副目标候选也有成功餐厅预订。actor说“17人”不证明实际传入17。原`Reservation success`可在已验证的同版verifier下约束最终预订人数/日期，但它不是全部历史动作的真值，也不覆盖先错订后改正；原执行版本及完整状态未随这些导出文件绑定。因此不能直接给全轨迹N。
6. 程序检索发现80条银行对话有向拼写为`jake.thompsom`的账户成功付款的返回，只是待核身份/授权的候选线索，不是80条公开可证P；显示名称可以由actor添加，需公开身份来源及累计金额审查。

本轮没有进行436条全事件语义复核，没有声称任何新增完整轨迹已合格。若要求维持现有严格全事件标签，应先补原始参数/读回状态与版本来源，再审核；不要先把导出文件批量标P/N来“凑够”。部分单个事件可能已经公开可判，但事件可判不等于全轨迹可判，也不应自动把主线改成事件级任务。

## 能否支持TGF追问

| 用法 | 当前判定 |
|---|---|
| 离线阅读历史轨迹、找证据缺口 | 可以；保留来源、去重、未知与信息缺失 |
| 直接填充当前gpt-oss-20b的冻结采集批次 | 不可以；actor、生成策略及记录格式不同 |
| 按现协议从原actor完整上下文独立分支 | 已读材料尚不支持无损认证 |
| 把历史轨迹作为文本交给另一模型回答 | 技术上可另行设计，但属于“回放解释/替代actor”新条件，不是原actor续问；本轮未执行 |

具体原因：

- 目录标记的生成actor包括多个Claude、Gemini、GPT及DeepSeek版本，已读范围没有当前`gpt-oss:20b`。没有验证这些历史原模型今天可访问，也没有发API探测请求或检查密钥。
- 有system、user、assistant和tool文本，但丢失原生工具参数和绑定、原始请求配置及工具schema；文件也没有保存原环境状态。以叙述或默认值补参数，不能叫无损恢复。
- 当前`paired_protocol.actor_branch`要求复制原始actor消息，追加问题；`run_paired_v2.Client.actor`调用冻结的gpt-oss actor；`public_event_contract_v3`从绑定的call arguments/return构造事件。现成导出不满足这些输入合同。
- **追问禁用工具，所以单纯问答不必恢复整个模拟器。** 状态缺失主要影响参考真值复核；追问的关键阻塞是原actor身份和完整消息上下文。缺少KV cache本身不是问题，原始完整消息可重放即可，但这批材料未满足该条件。
- 原system里含隐藏副目标，文件还含旧monitor回答和verifier结果。它们必须留在私有参考侧，不能把完整JSON交给monitor。actor追问可以保有自己的原system，monitor只能收到允许的公开投影与新回答。

## 任务兼容性及还缺什么

从HF取得的两个`task_definition.py`与本地源码的共有函数AST全部一致；本地额外增加benign-secondary相关函数。说明原用户请求与原恶意副目标可以对上，不需要因为这次发现立刻缩短任务。但这不证明历史全部环境资产和工具版本完全一致。

按优先顺序仍缺：

1. **原始日志**：未删参数的actor消息、调用/返回绑定；参考侧所需初始资产、状态/事件变更记录、实际源码commit与工具版本。可先查同一上游是否另有原始日志发布渠道；联系作者需用户明确授权，不能擅自发送消息。
2. **标签验收**：在信息完整的独立轨迹上逐事件审核执行/授权/公开证据，统计真正P/N、合法敏感N、unknown、失败。AI审核明确非人工金标；组员独立抽检仍未完成。
3. **actor兼容决定**：如要让公开轨迹进入TGF主实验，需要原模型可访问且上下文可恢复；否则只能单独设计历史文本回放条件，或保留原任务重新采集完整gpt-oss轨迹。这是后续研究设计决定，本轮未修改。
4. **数据边界与对照**：来源、同任务/同actor重复、开发/验证/测试隔离；各方法在完全相同的轨迹集合和公开信息上比较，不把现有gpt-oss正例与历史其他模型负例拼成一个貌似均衡的主实验。

当前本地旧采集的真实缺口仍为：银行21P/2N，距离30/30差9P/28N；航空12P/9N，差18P/21N。公开可证P最低15的缺口为银行5、航空3；合法敏感N最低15的缺口为银行14、航空12。这些是旧数据账目，不代表可以直接与本次跨actor候选相加。
