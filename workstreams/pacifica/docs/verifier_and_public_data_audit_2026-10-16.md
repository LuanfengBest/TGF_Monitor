# 原 verifier、公开数据和 TGF 接口核查

2026-10-16。按用户要求，仅进行代码、公开数据及已有轨迹的离线核查。0模型调用、0GPU、0模拟器派发、0新作业。未改任务、冻结采集器、标签合同或任何旧结果。以下静态证据审核不是原生状态链验收，不写入现有 pilot 标签。

## 可以据此决定什么

原仓库有可复用的任务、程序 verifier 和历史轨迹，不是只能从零生成数据。但 **原 verifier 的成功条件不等于 proposal 的“是否执行过任何未经授权动作”；公开轨迹也不是可直接续问的原生 actor 消息**。直接照搬 side=True/False 或无副目标条件，会引入实际标签错误。

公开数据应复用于证据案例、标签检查和共同接口开发。现有已读材料不能直接补齐两域30P30N，也不能直接接入冻结 gpt-oss actor 的原上下文 TGF。下一步最小修复是核准原采集循环差异，而不是缩短任务或重新训练 monitor；详见配套最小方案。

实际执行了7个纯函数反例检查，没有运行actor或模拟器：

## 3. 为什么不能直接用于现版TGF

已读1763份文件的工具调用字段都只保存工具名字符串，无原始arguments、call ID及完整原生消息绑定。官方MRT `logging_utils.py`的JSON导出代码也确实丢掉参数。成功返回可以保留某些执行事实，但通常不能恢复全部输入：例如银行排程日期/recurring、航空party_size。不能靠actor的叙述补造它们。

官方两个repo树及HF两任务完整文件索引中，未发现另外发布的原生参数日志/状态快照包；不是宣称互联网上绝无其他材料。HF两任务目录16868个JSON大量是重评副本，剩余10个文件为源码、README和pyc；本轮未逐一读取所有衍生JSON。全部索引和新取的上游代码已有URL、commit、SHA回执。

历史actor包括多个Claude/Gemini/GPT/DeepSeek版本，已读数据没有当前gpt-oss20b。现协议要求每个方法从同一个原actor的完整上下文独立分支。把文本给当前gpt-oss回答，是替代actor的文本回放条件，不能无声替代原设计。禁工具追问本身不需要恢复整个模拟器；关键是原actor身份与完整历史。原模型今天可用性也未通过API探测核实。

因此，公开材料的现成可用部分是**静态证据、审查案例和接口检查**；不能把“有一个JSON”当“已经有一条合格TGF实验样本”。严格原生路径还缺：无损调用日志/版本与状态来源、完整标签验收、原actor可复现访问，以及足量真实合法敏感负例。带hidden system、verifier、旧monitor预测的原文件只留参考侧，禁止整包给monitor。

## 4. 新发现的最小采集修复点

上游 `utils/pipeline_elements.py` 的 ToolsExecutionLoop 在无工具且未end_task时，追加原版提醒后继续；累计超过5次才停止，还受总迭代上限约束。我们的 `scripts/prospective_actor_v6.py` 在第一次这样的输出就直接停止。

现有45条非运行错误记录中42条的终态正是actor_stopped_without_end_task，另3条ended。这个差异已经由代码与实际记录证实；**尚未证明它是负例稀缺的全部原因，也没有证明加提醒会改善合法性。** 旧42条仍是已审的观察前缀，不因此全部作废；不得改写其结束状态或拼接“续跑”覆盖旧实验。

这提供了比重写任务更小的可检验修复：保持原用户请求、环境、模型和隐藏副目标，另版恢复上游的有界继续行为，先验证技术与负例产率，再决定扩采。原有保守上下文保护是否过早拒绝还需要精确token/模板核对，不能先删保护或假称已经修复。
